## Production integration gates

1. Review each real trigger body privately alongside its event/WHEN/UPDATE OF clauses,
   target defaults/generated columns, unique/index predicates, FK/check definitions
   and deferral. Establish which exact statement writes each history/payment/status
   row and what prevents duplicates. An ON CONFLICT spelling or valid index alone
   is not deduplication proof. Identify external FK targets rather than ignoring them.
2. Reproduce those verified contracts in fictional fixtures. Current synthetic
   history/payment/status triggers are explicitly NOT the LIVE implementations.
   The new finish/start failure regressions prove transaction rollback of archives,
   revisions, closure, projection, ledger and status within the fixture only.
3. Retain one committed group row as canonical data in production. Under its row
   lock, enforce first-score closure, frozen entrants/payment/pot projection, and
   expected round/revision for every save. Protected organiser finish/start must
   use that same lock order and transaction. Do not duplicate real trigger payouts
   in the adapter or treat a history-reset shape as authorisation.
4. Keep group-scoped hashed, expiring/revocable credentials separate from shared
   PINs, global creation codes and caller-set GUCs. Production issuance/recovery,
   transport/storage, retry receipts and ALL-group/device coverage remain unbuilt.
5. Finish the actual client bridge for revisioned save/read, protected finish/setup,
   conflicts, delayed payment return and queued requests. Synthetic harness routing
   is not a production client. Preserve Side Game, League, Trip and maintenance.
   Full adversarial results validation and unsupported legacy Trip shapes remain open.

## Proposed migration and rollback — not executable SQL

- Bind reviewed exact legacy signatures/columns/owners/privileges; check expected
  catalog hashes and version under controlled writers before changing anything.
- Add private round/revision/closure and capability metadata with explicit minimum
  grants (no automatic Data API grant assumptions). Prefer lazy initialisation under
  the canonical row lock, derived from existing scores without rewriting group JSON.
  Existing completed history and payment records remain unchanged.
- Create reviewed fixed-path validators/protected transition RPCs and a central
  table-write boundary covering ordinary, Admin, owner/service and recreation paths.
  Keep compatible real trigger semantics and ordering; do not replace them with
  synthetic fixture functions. Activate only after credential/client readiness.
- Atomic bounded installation, exact baseline guards and ON_ERROR_STOP. A failed
  installation must roll back catalog and data effects. Verify actual ownership and
  managed-trigger authority before claiming rollback executable.
- Generate object restoration from exact saved definitions, ACLs, owners and trigger
  state; preserve default ACL/effective-role differences. No CASCADE, old JSON restore
  or deletion of populated metadata. After writes, prefer forward repair or retain a
  compatible fail-closed boundary: dropping it would reopen late entry. Archive,
  revocation and newly completed results must survive rollback.
- Fresh target-specific backup/checksum, recovery rehearsal including security,
  protected-data fingerprints and writer controls need separate approved preflight.
  Original LIVE catalog evidence and historic TEST backups are not current TEST
  identity/schema/data parity or complete recovery proof.
